# IIDX 六维图调研

调研日期：2026-10-30。本文是资料整理与后续设计建议，没有启用新算法。

## 结论与证据等级

需要分开两层：谱面六维描述音符结构；玩家六维描述在这些谱面上的表现。不能直接把等级或现有 rating 复制为六个轴。

### 官方已公开的六项含义

来源：[IIDX 33 官方游戏画面说明](https://p.eagate.573.jp/game/2dx/33/howto/play/game_screen.html)，页面“ノーツレーダー”部分。

| 项目 | 中文含义 | 官方说明的重点 |
| --- | --- | --- |
| NOTES | 整体密度 | 总音符数相对于歌曲时长的多少 |
| CHORD | 同时押 | 同时押的难度 |
| PEAK | 局部爆发 | 瞬间音符密度 |
| CHARGE | 长按复合 | 长按与长转盘的难度 |
| SCRATCH | 转盘 | 转盘音符相对于歌曲时长的多少 |
| SOF-LAN | 变速识别 | BPM 改变时的音符难度 |

官方说明玩家值随谱面雷达与游玩结果增长，但上述说明没有给出从音符计算谱面各轴的完整数值公式。

[官方排行榜](https://p.eagate.573.jp/game/2dx/33/ranking/notes_radar/index.html) 将 SP、DP 分开，并列出六轴与综合值。

### 可核对的民间计算工具：玩家汇总

来源：[作者发布的 IIDXScore2Radar](https://masaoblue.github.io/iidx-score-to-radar/)。本次也读取其实际发布的 [页面脚本](https://masaoblue.github.io/iidx-score-to-radar/assets/home-DYsm52sw.js)，只作源码分析，没有执行第三方程序。

观察到的实现：

1. 读取独立的歌曲／难度属性表，而非现场从谱面重新求属性值。
2. `EX得分率 = EX_SCORE / (2 × notes)`。
3. 每个轴的单谱面贡献为 `谱面该轴数值 × EX得分率`。
4. 各轴分别排序，同一首歌的不同难度去重，最多取十首。不同轴的入选歌曲可以不同，同一首歌可以贡献多个轴。
5. 工具对单项值向下截断到两位小数后求平均，并再次截断；满十首时为各贡献之和除以十，综合为六轴之和。
6. 该工具不足十首时除以实际数量。这是工具实现，不能直接断言等同现行官方规则；缺位策略、版本差异及精度顺序需要用官方样本进一步核验。

例：某谱面 CHORD 属性为 160，EX 得分率为 95%，该次该轴贡献为 152。此后还需要参与 CHORD 轴自己的 Top10 汇总。

注意：不能用 Malody 的原始总分直接代入 IIDX 的 EX_SCORE；两者计分方式不同。准度、判定等级怎样折算，应单独定义并校准。

### 可执行的民间谱面分析实现：并非官方公式

来源：[laochan-eacnet/client 的 analyze.cpp](https://github.com/laochan-eacnet/client/blob/master/src/client/component/iidx/analyze.cpp)。其 raw 数据处理和阈值归一化属于该项目的实现，不能标为 KONAMI 官方原式。

代码值得借鉴的特征选择包括：平均密度；一秒峰值与相邻三秒密度；快速重复转盘加权；多键同押非线性加权；长按期间伴随击键；变速后短时音符密度，并对这些 raw 特征分段归一化。它与部分社区对时间窗口的描述存在差异，因此不应照搬为官方数值。

另找到研究者 yonexun 的[讨论汇总链接](https://posfie.com/@yonexun/p/f968ULu)，本次未能读取内容；不作为具体公式已验证的证据。

排除项：[BPIManager2 radar/calculator.ts](https://github.com/BPIManager/BPIManager2/blob/master/src/lib/radar/calculator.ts) 按属性分类计算 BPI，属于另一种统计口径，不能误当 IIDX 官方 Notes Radar 公式。

## 用户确定的 Malody 六轴定义（2026-10-30）

以下为用户指定的项目定义，优先于前文 IIDX 的属性含义。物量按总数量，不改成平均密度；长按复合目前按直长条数量，不额外加入伴随击键权重。

| 轴 | 已确定的统计含义 | 需保留的原始数据 |
| --- | --- | --- |
| 物量 | 歌曲总 note 数量 | 总 note 数；原始音符数与长按尾／折点等派生计数分开保存，最终 note 口径需对照游戏 |
| 同押 | 3 压、4 压的数量 | 三押组数、四押组数分别保存；同一时刻的四押只算一组四押，不拆成三押组合 |
| 爆发 | 某段时间内达到的最大音符密度 | 峰值窗口长度、窗口起止时间、音符数、notes/s |
| 长按复合 | 直长条数量 | 直长条条数；带折线的滑键不直接当成直长条重复统计 |
| 滑键 | 用户指定的滑键计数点密度 | 中途转角数 + 末端箭头落点数；不计起始按键位置与直线上的冗余控制点 |
| 变速 | 变速或变 BPM 的频率 | BPM 有效变化、滚动速度有效变化的时间序列及合并事件数 |

### 实现建议与待确认项（不视为用户已确认）

- 爆发先试算真实时间的 4 秒滑动窗口，并保留 1 秒、2 秒辅助数值以便人工对照。窗口内多键同押按实际音符数量计入，不能只算一次击键时刻；不能固定分桶导致跨桶爆发被切开。
- 滑键计数已由用户示意图明确：中途每个转角计 1 点，末端箭头落点也计 1 点；起始按键位置不计，同一直线上的冗余控制点不计。箭头图形的两翼不是额外转角。示意图从左到右分别为 2 点、1 点、4 点，因此单次直滑也计 1 点。此前“终点不计”的建议已被本规则替代。解析时需结合实际滑键路径识别这些点，不能简单将 `seg` 数量视为结果。
- 滑键密度可先用上述计数点总数 / 谱面有效时长（秒）；是否改为局部峰值尚未确定。
- 变速频率可先用有效变化事件数 / 谱面有效时长（分钟）。初始 BPM／初始速度不算一次变化，相同值重复事件忽略，同一时刻 BPM 和滚速一起变化按一次合并事件，同时保留各自数量。变速幅度可以作为详情展示，不自动加入该轴权重。
- 谱面有效时长暂建议采用首个可玩音符至最后一个可玩音符结束的真实秒数，避免音频尾部静音拉低频率；正式实现应保存时间口径和算法版本。
- 同押先保留三押、四押两项原始数量，合成为一轴时的权重尚未定。6K 中五押、六押如何归属也尚未定，不静默改成四押。
- 六个原始量的单位不同，不能直接作为六边形半径比较；需用代表性谱面建立固定标定，4K／6K 分开校准。玩家准度／判定贡献公式仍另行定义。

## 对 Malody Link 的结构建议（尚未定稿）

- 结构采用“谱面属性 → 成绩折算贡献 → 每轴独立 Top10 → 六边形显示”。维度榜不要只从 B30 的三十首中抽取，应扫描当前服务器全部有效成绩。
- 继续按歌曲身份去重；4K 与 6K 独立计算，避免不同键数天然密度差异挤占榜单。
- 六轴采用上文用户定义的物量、同押、爆发、长按复合、滑键、变速。这是我们的适配设计，并非 IIDX 原定义。
- 谱面特征在服务器按谱面 hash 与算法版本预计算；成绩同步后服务器计算玩家六维，App、机器人共用结果，降低手机负担。
- 保留各轴入选歌曲与贡献明细，让玩家能解释每个数值。
- 当前项目远端已新增 rating v3；后续设计必须沿用或明确另定准度／判定折算，不能误用旧版系数，也不要自动改变现有 O20+N10 rating。

## 实现前还需明确

1. 同押合成权重与 6K 五押／六押归属。
2. 特征的时间窗口、长按／滑键计数方式；采样以真实秒数还是拍数为准。
3. raw 特征到展示尺度的固定标定；不能每次随新歌加入而漂移。
4. Malody 准度、判定与贡献系数的对应方式；辅助选项是否排除。
5. Top10 不足时的缺位策略、同曲身份以及跨键数隔离规则。

建议先用代表性谱面离线出表并人工核对，再接入 App 与机器人；本次不修改线上 rating 或部署六维功能。
